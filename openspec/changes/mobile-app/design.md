# Design

## Context

See proposal.md (Why). Requirements are in `specs/mobile-experience/spec.md` and `specs/app-shell/spec.md`.

Current state: `crates/notebook-app` is a Tauri 2 crate already built as `staticlib`/`cdylib`/`rlib` with a `#[cfg_attr(mobile, tauri::mobile_entry_point)] run()`, one `core:default` capability, a strict CSP, and iOS/Android icons. There is no `gen/apple` or `gen/android` project yet. The frontend (`web/`, Svelte 5 + Vite) has a `platform/` folder meant for Tauri-vs-WASM branching. CI (`.github/workflows/ci.yml`) runs web checks, Rust fmt/clippy/tests on Linux, and a wasm32 core build.

This change lands after, and builds on, sibling changes that are not implemented yet:
- `desktop-app-shell`: the `app-shell` capability, the Tauri command/event surface, the three-pane layout, and keychain credential handling (refresh token plus wrapped key material, unlock on launch, explicit lock).
- `note-editor-component` / `editor-live-preview`: the CodeMirror 6 editor, its Yjs binding to the core, vim compartment, and live-preview decorations.
- `sync-client-engine` and `local-sqlite-storage`: outbox, pull/push, live mode, status, device-local settings.
- `markdown-export`: the core export module and its zip output.

Where this design names an interface from those changes, it means "whatever that change ships"; the mobile work adapts to it rather than redefining it.

## Goals / Non-Goals

**Goals:**
- One crate and one frontend for desktop and mobile. Mobile-only code is confined to a plugin crate, `#[cfg(mobile)]` blocks in `notebook-app`, `web/src/platform/`, and a few layout/toolbar components.
- Every secret on the phone is either in memory (unlocked) or held by the OS secure hardware path (Keychain / Keystore).
- No data loss across backgrounding, suspension, or OS termination.

**Non-Goals:**
- App Store / Play Store submission, TestFlight, release automation. CI builds unsigned debug artifacts only.
- A share extension that receives text from other apps into a note, home-screen widgets, push notifications, iPad multi-window (multiple scenes), and Apple Watch / Wear OS.
- Swipe actions on note-list rows (long press covers the actions in this change).
- Exporting to a chosen folder on mobile (see "Export through the share sheet").
- Encrypting the local SQLite file with a separate key. Its contents are already ciphertext (`local-storage`).

## Decisions

### Responsive layout is an `app-shell` concern, at 900 CSS px

The stacked layout is driven purely by viewport width, not by "is mobile", so the browser client on a phone and a narrow desktop window get it too. 900 px keeps iPad landscape (1024–1366) and most desktop windows on three panes while iPad portrait (768–834) and phones stack. A single navigation store holds `{ view/tag, openNoteId }`; the layout component derives which pane(s) to render from it plus a `matchMedia('(min-width: 900px)')` signal, so rotating or resizing never loses state (spec: "Layout changes keep context").

The editor component instance is kept mounted across layout switches (moved between containers, not recreated) so the caret, undo history, and Yjs binding survive.

**Alternative considered:** a separate mobile route tree. Rejected: two navigation models drift, and the browser-on-phone case would need it too.

### Stack navigation via the History API

Each step down the stack does `history.pushState({ level })`; `popstate` moves up. This gives uniform behavior for the visible back control (calls `history.back()`), browser back on a phone, the Android system back (Tauri's Android WebView activity navigates WebView history when it can and otherwise finishes, which backgrounds the app), and iOS edge-swipe back, which `WKWebView.allowsBackForwardNavigationGestures` provides for same-document history entries. The plugin turns that property on at startup. No URL path changes, since the browser client is served from `/` and deep links into notes aren't in scope.

On a wide layout no stack entries are pushed. When the layout switches, the history entries are rebuilt to match the visible level (`replaceState` plus pushes) so back never jumps to a stale level.

**Alternative considered:** a hand-written edge-swipe recognizer in JS. Kept only as a fallback if the WKWebView gesture proves unreliable with SPA history (see Risks).

### One in-repo plugin: `tauri-plugin-notebook-mobile`

A new workspace crate `crates/tauri-plugin-notebook-mobile` (generated by `tauri plugin new`, with `ios/` Swift package and `android/` Kotlin library) owns all native mobile code:

| Area | iOS | Android |
|------|-----|---------|
| Secure store | Keychain generic-password items | AES-256-GCM key in AndroidKeyStore, ciphertext in `noBackupFilesDir` |
| Device auth availability | `LAContext.canEvaluatePolicy(.deviceOwnerAuthentication)` | `BiometricManager.canAuthenticate(BIOMETRIC_STRONG or DEVICE_CREDENTIAL)` + `KeyguardManager.isDeviceSecure` |
| App-switcher privacy | overlay view on `willResignActive`, removed on `didBecomeActive` | `FLAG_SECURE` on the activity window |
| Background flush time | `beginBackgroundTask` / `endBackgroundTask` | none needed (process keeps running briefly; outbox is durable) |
| Quick capture | `UIApplicationShortcutItems` in Info.plist, action observed by the plugin | static `shortcuts.xml` firing a `VIEW notebook://new` intent |
| Share | `UIActivityViewController` | `Intent.ACTION_SEND` via `FileProvider` |
| Back gesture | `allowsBackForwardNavigationGestures = true` | default WebView back handling |

It exposes Rust APIs (used by `notebook-app`) and a few permissioned commands (used by the frontend: share, privacy toggle). On desktop the plugin is not registered.

The `notebook://new` link uses `tauri-plugin-deep-link` (official, supports iOS and Android). The Android app shortcut routes through the same deep link, and the iOS quick action is translated by the plugin into the same internal `quick-capture` event, so there is one handler.

**Alternatives considered:** community `keyring`-style plugins and `tauri-plugin-stronghold`. `keyring` has no Android backend and can't set iOS access-control flags; stronghold stores a file encrypted with a key we would still need to protect. `tauri-plugin-biometric` only prompts and can't bind release of a secret to authentication, so it would make the lock a UI gate rather than an OS-enforced one. A separate plugin per feature was rejected as needless crate sprawl.

### Credentials: a mobile `CredentialStore` with two protection levels

`desktop-app-shell` already defines a `CredentialStore` trait (desktop: `keyring`; in-memory for tests) with three entries: the refresh token, `local-unlock` (Argon2id salt plus the vault key wrapped under the passphrase-derived key, for offline passphrase unlock), and `auto-unlock` (the vault key itself, present only while signed in and not locked). Mobile adds a `CredentialStore` implementation over the plugin and a per-entry protection level, without changing the entries or desktop behavior:

| Entry | App lock off | App lock on |
|-------|--------------|-------------|
| refresh token | Standard | Standard |
| `local-unlock` | Standard | Standard |
| `auto-unlock` | Standard | **DeviceAuth** |

Only `auto-unlock` is gated, because it alone opens the vault without the passphrase. Keeping the refresh token and `local-unlock` at Standard means losing DeviceAuth items (passcode removed) still leaves offline passphrase unlock working (spec: Fallback to passphrase unlock), and sync can resume after unlock without an extra prompt.

Platform mapping:
- **Standard:** iOS `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`; Android Keystore key with `setUnlockedDeviceRequired(true)`, no user auth.
- **DeviceAuth:** iOS `SecAccessControl(kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly, .userPresence)`; Android Keystore key with `setUserAuthenticationRequired(true)` and `setUserAuthenticationParameters(0, BIOMETRIC_STRONG | DEVICE_CREDENTIAL)`, decrypted through `BiometricPrompt` with a `CryptoObject`.

`ThisDeviceOnly` items and Keystore keys never leave the device, so a restored backup has nothing to unlock with and the app starts signed out. The Android ciphertexts live in `noBackupFilesDir`; they're useless without the hardware-bound key but are still kept out of backups.

`.userPresence` (biometrics or passcode, not invalidated by new enrollments) rather than `.biometryCurrentSet`: adding a biometric already requires the passcode, and the passcode is an accepted fallback anyway, so invalidating on enrollment would cost users a passphrase entry without stopping anyone. When the passcode is removed, iOS deletes `WhenPasscodeSet` items and Android permanently invalidates the key. The store reports "entry lost", the app deletes the remainder, turns app lock off, and shows passphrase unlock. The SQLite outbox is untouched, so pending edits survive.

Turning app lock on prompts once and rewrites `auto-unlock` at DeviceAuth. Turning it off reads it (prompting) and rewrites it at Standard.

**Lock kinds.** desktop-app-shell's `Locked` phase is reused for both kinds. The explicit Lock action keeps its app-shell meaning: delete `auto-unlock`, record the locked hint, and require the passphrase (spec: Explicit lock on mobile). **Auto-lock** drops the `Workspace` (keys zeroize, sync stops) but keeps `auto-unlock`. The lock screen therefore offers device authentication only when a DeviceAuth `auto-unlock` entry exists, plus the passphrase path always. On launch, desktop's rule "entry with an auto-unlock key → unlock directly" becomes, on mobile with app lock on, "show the lock screen and prompt immediately". The read itself triggers the OS prompt, so no note content is loaded before authentication.

**Alternatives considered:** gating all three entries behind DeviceAuth (breaks offline passphrase fallback after passcode removal); and deleting `auto-unlock` on auto-lock, as explicit lock does (then device authentication would have nothing to release).

### Android minimum SDK 30

`setUserAuthenticationParameters` with `DEVICE_CREDENTIAL` as a per-use authenticator needs API 30. Below that, passcode fallback requires time-bound keys, which weakens the "released only after auth" guarantee. API 30 (Android 11) is the floor; iOS uses Tauri's default deployment target (iOS 14+), which supports everything above.

### Lifecycle is detected in the webview, decided in Rust

`AppState`'s phase (`desktop-app-shell`) already models `Locked` / `Unlocked { workspace }` and emits `app-phase-changed`, and the frontend renders the unlock screen from it. Mobile adds an `auto_lock()` transition (described above) and a device-auth `unlock_with_device()` command.

Foreground/background detection uses `document.visibilitychange` in the webview, which fires reliably in WKWebView and Android WebView, and calls commands:
- `app_backgrounded`: begins a background task (iOS), flushes the editor (`NoteEditorHandle.flush()`) and outbox, records `backgrounded_at = SystemTime::now()`, and if the delay is "immediately", locks.
- `app_foregrounded`: if app lock is on and `now - backgrounded_at` exceeds the delay, or is negative (clock moved back), auto-locks before the UI shows any content and presents the lock screen; otherwise triggers an immediate pull and resumes live mode.

Wall clock is used because monotonic clocks on iOS stop during device sleep, so they'd under-count time away. The privacy overlay is applied natively (the plugin's `willResignActive` hook), because it must be in place before the OS takes the snapshot, which happens before JS can react.

A cold launch with app lock on always presents the lock screen, since the blob is only readable after auth.

**Alternative considered:** Tauri `RunEvent::Resumed` and similar Rust-side lifecycle events. Their coverage differs by platform and version. `visibilitychange` is uniform and also covers the browser. The plugin can forward native events later if a gap appears.

### Flushing on background

The editor already sends each Yjs transaction to the core (note-editor bridge). The only pending state is any debounce in that bridge, so the frontend calls `NoteEditorHandle.flush()` before invoking `app_backgrounded`, then the core persists to the outbox (`local-storage` makes that durable) and attempts a push. On iOS this runs inside a `beginBackgroundTask` window (about 30 s) that ends when the push finishes or the expiration handler fires. Nothing depends on the push finishing: the outbox is retried on the next sync (spec: flush on background).

### Touch toolbar and formatting commands

Formatting actions are pure CodeMirror transactions in the editor package (`web/src/editor/formatting.ts`: `toggleWrap('**')`, `toggleWrap('*')`, `cycleHeading`, `toggleBullet`, `insertTag`, `makeLink`), so they can be unit-tested on an `EditorState` without a DOM and reused for desktop keyboard shortcuts later. The task button reuses `editor-live-preview`'s toggle-task command, extended so a line with no list marker gets `- [ ] `, rather than defining a second task semantic. Undo/redo call `NoteEditorHandle.undo()/redo()` (local-only, per `note-editor`).

The toolbar is a Svelte component shown when the editor has focus, the pointer is coarse, and the keyboard is visible. Keyboard visibility and position come from the `visualViewport` API: iOS shrinks the visual viewport but not the layout viewport, so the toolbar is positioned at `visualViewport.offsetTop + height`. Android uses `adjustResize` plus `<meta name="viewport" content="..., interactive-widget=resizes-content, viewport-fit=cover">`. Buttons call `preventDefault()` on `pointerdown` so the editor keeps focus and the keyboard stays up. The editor's scroll container gets bottom padding equal to toolbar height plus safe-area inset, and `EditorView.scrollIntoView` runs on viewport resize, which satisfies the caret-visibility scenarios.

Tag insertion uses the core tag parser's rules (via the existing core binding) to decide whether a selection needs the closing `#`.

**Alternative considered:** a native `inputAccessoryView` toolbar on iOS. It's more native, but there's no Android equivalent, and it can't call CodeMirror without an IPC round trip per tap.

### Safe areas

`viewport-fit=cover` plus `env(safe-area-inset-*)` padding on the app frame and the toolbar. Android WebView's `env()` support for display cutouts varies by WebView version, so the plugin also publishes the window insets from `WindowInsetsCompat` as CSS custom properties (`--sai-top` etc.), and the CSS uses `max(env(...), var(--sai-...))`.

### Live preview on touch

No new rendering. `editor-live-preview` already reveals syntax on the active line and maps positions through CodeMirror. This change adds touch-specific handling: the checkbox widget handles `pointerdown` itself (toggling the underlying text through a transaction) and returns `true` from `ignoreEvent` so CodeMirror doesn't focus the content (which would raise the keyboard). Tap-to-caret uses CodeMirror's default `posAtCoords`. Native selection handles operate on the real DOM text, and hidden syntax is collapsed by `Decoration.replace`, so selections map to underlying ranges. Tasks include on-device checks for each spec scenario.

### Quick capture

The deep-link handler parses the URL and accepts only host `new`, ignoring everything else (spec: content-free). The resulting `quick-capture` intent is queued in the frontend until the vault is unlocked, then selects Notes, calls the app-shell create operation (`Workspace::create` with no tag, so the note is empty), navigates to the editor, and focuses it via `NoteEditorHandle.focus()`. WKWebView normally raises the keyboard for programmatic `focus()` only during a user gesture. The quick action itself counts as one only if focus happens promptly, so the frontend focuses the editor in the same turn it handles the event, and the plugin delivers the event once the webview is active. If on-device testing shows that isn't enough, see Risks.

The note is marked "quick capture" in frontend state. If the user leaves the editor while its body is still empty, the app purges it (`Workspace::purge`) directly. This is the internal purge, not the user-facing "Delete permanently", which is limited to Trash and asks for confirmation. Nobody else has seen an empty note, so there's nothing to confirm. The create and purge may both reach the server if a sync ran in between, which is harmless.

### Export through the share sheet

The core's zip output is used unchanged. `notebook-app` writes the bytes to `<temp>/exports/notebook-export-….zip` (iOS temp directory with `NSFileProtectionComplete`; Android `cacheDir/exports` exposed through a `FileProvider` restricted to that folder), calls the plugin's share, and deletes the file when the share completion callback fires. On launch, `exports/` is emptied in case the app was killed mid-share. The desktop folder output is not offered on mobile.

### Backups

iOS: the app data directory (Tauri `app_data_dir`, under Application Support) gets `isExcludedFromBackup` at startup. Android: `android:allowBackup="false"`, `android:fullBackupContent="false"`, and `dataExtractionRules` excluding all domains for cloud backup and device transfer.

### Capabilities and permissions

`capabilities/default.json` gains `"platforms": ["macOS", "windows", "linux"]`. A new `capabilities/mobile.json` (`"platforms": ["iOS", "android"]`) grants `core:default`, the plugin's `share` and `privacy` commands, and `deep-link:default`. The CSP is unchanged: sync runs in Rust (`reqwest` with `rustls`, so no OpenSSL cross-compilation), not via webview `fetch`.

New platform declarations, each with a reason:
- iOS `NSFaceIDUsageDescription` ("Unlock Notebook with Face ID"), required for Face ID prompts.
- iOS `CFBundleURLTypes` for `notebook`, and `UIApplicationShortcutItems` for New Note.
- Android `USE_BIOMETRIC` permission (normal, install-time), the `notebook` intent filter, and the shortcuts metadata.
- `INTERNET` is already in the Tauri Android template. No camera, contacts, location, or notification permissions.

App lock settings (enabled, delay) are device-local settings in `local-storage`; they aren't secret.

### Build and CI

`cargo tauri ios init` and `cargo tauri android init` output is committed under `crates/notebook-app/gen/{apple,android}` (Tauri's recommendation; Info.plist and manifest edits live there). Two CI jobs:
- `ios` on `macos-latest`: add `aarch64-apple-ios-sim`, install `tauri-cli`, run `cargo tauri ios build --debug --target aarch64-sim` (simulator builds need no signing).
- `android` on `ubuntu-latest`: `setup-java` 17, Android SDK and NDK, targets `aarch64-linux-android` and `x86_64-linux-android`, run `cargo tauri android build --debug --apk`.

Both download the `web-dist` artifact like the `rust` job. `docs/mobile.md` covers local setup, simulator/emulator runs, and how signing would be configured for a release build.

## Risks / Trade-offs

- [WKWebView swipe-back may not reliably reflect `pushState` entries or may animate oddly] → Verify early on a device (task 3). Fallback: a JS left-edge swipe recognizer that calls `history.back()`.
- [iOS gives roughly 30 s of background time, and the OS can kill the app at any time after] → The outbox is persisted before the push attempt, so the cost is latency, not data. The spec only promises local durability.
- [Programmatic focus may not raise the iOS keyboard on quick capture, especially after a device-auth prompt] → Verified on device in task 7.3. If it can't be made reliable, the implementer stops and reports so the spec scenario can be relaxed to "editor focused, one tap raises the keyboard" rather than silently shipping less.
- [`FLAG_SECURE` also blocks screenshots and screen recording while app lock is on] → Accepted. It's the only reliable way to hide Android recents previews. It's tied to app lock so users who don't want it aren't affected.
- [Android WebView safe-area `env()` gaps] → Plugin-published inset variables as described above.
- [CodeMirror plus IME/autocorrect quirks (Gboard composition, iOS dictation) interacting with Yjs] → On-device checks for composition and autocorrect in tasks. CodeMirror 6 handles composition natively; issues get filed upstream or worked around in the editor package.
- [Android min SDK 30 excludes Android 10 and older] → Accepted for security reasons (above). Revisit only if real users need it.
- [Wall-clock auto-lock can be fooled forward or backward] → Moving the clock backwards locks. Moving it forwards only locks sooner. Neither can unlock.
- [The `app-shell` capability exists only as `desktop-app-shell`'s delta] → This change MODIFIES its "Three-pane layout" requirement, copied from that delta. `openspec validate` notes that archive needs the main `app-shell` spec, so `desktop-app-shell` must archive first (it does, per `TODO.md`). Re-diff the copied text against the archived spec before archiving (task 9.3).
- [`markdown-export` says native clients export to a user-chosen folder] → This change MODIFIES "Folder output" to say desktop clients, with mobile using the zip output through the share sheet. Like `app-shell`, it needs `markdown-export` archived first and a re-diff before archiving (task 9.3).

## Migration Plan

New platforms only. No data or schema migration. Desktop behavior is unchanged apart from the responsive layout on narrow windows and the per-entry protection level added to `CredentialStore`, which desktop ignores. Rollback is reverting the change; no mobile installs exist to migrate.

- Apple developer team and Android upload key for release signing: only needed when distribution is planned. CI here builds unsigned debug artifacts.
